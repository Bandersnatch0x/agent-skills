# 成谱

需求对齐了,但还没决定它怎样进入现有系统。这一站把「要什么」变成「放在哪、怎么观察、不做什么」。

## 何时使用

- 需求已经过拷问,决策落定,但还没有一份能被执行和验收的谱。
- 改动要跨模块、跨会话,靠聊天记录传给下一个会话会失真。
- 同一处判断在不同层各自实现,规则开始漂移。

## 怎么用

1. 只综合,不再访谈。缺的决策回抛,不自己补。访谈已经做完,这一站再问一遍只会让人烦。
2. 先读既有权威。裁决落点、术语表、同域既有规格,三样都读。新方案与旧裁决冲突时,要么改方案,要么显式推翻并记下理由,不能假装旧裁决不存在。
3. 全文使用术语表里的词。谱里一套词、代码里另一套词,是后面所有误解的源头。
4. 先定缝,再写方案。缝是测试住的公共边界,优先复用既有缝,缝越少越好,理想是一条。把「怎样验证」前置到设计阶段,而不是写完代码再补。
5. 缝定完先与人确认。确认前的缝不算数。
6. 按七节写:问题、方案、用户故事、实现决策、测试决策、范围外、补充说明。
7. 测试决策与范围外各自独立成节,不许合并进方案。这两节是唯一能挡住「没有观察点」和「顺手把能做的都做了」的地方。
8. 谱的终点不是一个文件,而是一组能被直接领走的票。写完之后应当不需要人再转述一遍。

**判据。** 一个没参与讨论的人,只读这份谱,能说出要改哪些层、在哪里观察结果、哪些明确不做。

## 边界

- 不做访谈。需要问的决策,退回拷问。
- 不切票,不估工作量。那是成票。
- 不做发布顺序与回滚。属于交付沉淀。
- 谱不许长成一份什么都想说的文档。范围外一节写不满,通常说明范围还没想清楚。
